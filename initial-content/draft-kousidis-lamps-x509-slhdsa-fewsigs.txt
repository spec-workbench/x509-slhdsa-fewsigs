Internet X.509 Public Key Infrastructure: Algorithm Identifiers for SLH-
         DSA with a Limited Number of Signatures (SLH-DSA-FEW)
            draft-kousidis-lamps-x509-slhdsa-fewsigs-latest

Abstract

   RFC 9909 specifies the conventions for using the Stateless Hash-Based
   Digital Signature Algorithm (SLH-DSA) in the X.509 Public Key
   Infrastructure.  NIST SP 800-230 adds six SLH-DSA parameter sets that
   are restricted to at most 2^24 signatures per signing key.  The
   security of these parameters depends entirely on adhering to this
   limit.  This document specifies the algorithm identifiers for these
   parameter sets in X.509 and updates RFC 9909 to address the much
   lower signature limit.

1.  Introduction

   [RFC9909] defines the conventions for the use of the twelve SLH-DSA
   parameter sets of [FIPS205] in the X.509 Public Key Infrastructure.
   These parameter sets are designed to be secure for up to 2^64
   signatures per key, which is the reason for their large signatures of
   7,856 to 49,856 bytes.

   [SP800-230] specifies six additional parameter sets for NIST security
   categories 1, 3, and 5 that reduce signature size and verification
   time by limiting a signing key to 2^24 (16,777,216) signatures; see
   [KP22] and [FD24] for background.  The resulting signatures are
   3,856, 7,752, and 14,944 bytes long, while signing is slower than
   with the parameter sets of [FIPS205].  If a key is used to generate
   more than 2^24 signatures, its security degrades below the security
   category of its parameter set, and degrades further with every
   additional signature.  [SP800-230] names signing of software,
   firmware, and digital certificates as the intended use cases, and
   states that these parameter sets are not approved for general-purpose
   use.

   This document refers to these additional parameter sets as SLH-DSA-
   FEW.  The corresponding pure version is referred to as Pure SLH-DSA-
   FEW, and the pre-hash version as HashSLH-DSA-FEW.  The signature
   algorithms are those of [FIPS205]; only the parameter sets differ.

   This document:

   *  defines the algorithm identifiers for the six SLH-DSA-FEW
      parameter sets, for both Pure SLH-DSA-FEW and HashSLH-DSA-FEW
      (Section 3),

   *  specifies how the conventions of [RFC9909] apply to them
      (Section 4),

   *  defines the associated ASN.1 module (Appendix A), and

   *  updates the Operational Considerations and Security Considerations
      of [RFC9909] to address the 2^24 signature limit (Section 5 and
      Section 6).

1.1.  Notation

   id-slh-dsa-*-24: A shorthand to refer to all six OIDs used to specify
   the different parameter combinations for Pure SLH-DSA-FEW.

   id-hash-slh-dsa-*-24-*: A shorthand to refer to all six OIDs used to
   specify the different parameter combinations for HashSLH-DSA-FEW.

3.  Algorithm Identifiers

   The AlgorithmIdentifier type and the meaning of its fields are as
   described in Section 3 of [RFC9909].

   The object identifiers for the SLH-DSA-FEW parameter sets are to be
   defined by NIST in the Computer Security Objects Register [CSOR].
   The same algorithm identifiers are used for identifying a public key,
   a private key, and a signature.  As in [RFC9909], there are separate
   identifiers for Pure SLH-DSA-FEW and HashSLH-DSA-FEW.

   The Pure SLH-DSA-FEW OIDs are:

      nistAlgorithms OBJECT IDENTIFIER ::= { joint-iso-itu-t(2)
        country(16) us(840) organization(1) gov(101) csor(3) 4 }

      sigAlgs OBJECT IDENTIFIER ::= { nistAlgorithms 3 }

      id-slh-dsa-sha2-128-24 OBJECT IDENTIFIER ::= { sigAlgs TBD1 }

      id-slh-dsa-shake-128-24 OBJECT IDENTIFIER ::= { sigAlgs TBD2 }

      id-slh-dsa-sha2-192-24 OBJECT IDENTIFIER ::= { sigAlgs TBD3 }

      id-slh-dsa-shake-192-24 OBJECT IDENTIFIER ::= { sigAlgs TBD4 }

      id-slh-dsa-sha2-256-24 OBJECT IDENTIFIER ::= { sigAlgs TBD5 }

      id-slh-dsa-shake-256-24 OBJECT IDENTIFIER ::= { sigAlgs TBD6 }

   The HashSLH-DSA-FEW OIDs are:

      id-hash-slh-dsa-sha2-128-24-with-sha256 OBJECT IDENTIFIER ::= {
         sigAlgs TBD7 }

      id-hash-slh-dsa-shake-128-24-with-shake128 OBJECT IDENTIFIER ::= {
         sigAlgs TBD8 }

      id-hash-slh-dsa-sha2-192-24-with-sha512 OBJECT IDENTIFIER ::= {
         sigAlgs TBD9 }

      id-hash-slh-dsa-shake-192-24-with-shake256 OBJECT IDENTIFIER ::= {
         sigAlgs TBD10 }

      id-hash-slh-dsa-sha2-256-24-with-sha512 OBJECT IDENTIFIER ::= {
         sigAlgs TBD11 }

      id-hash-slh-dsa-shake-256-24-with-shake256 OBJECT IDENTIFIER ::= {
         sigAlgs TBD12 }

   Each OID identifies the corresponding parameter set of Table 1 in
   [SP800-230]; for example, id-slh-dsa-shake-192-24 identifies SLH-DSA-
   SHAKE-192-24.  The pre-hash functions follow the pairing used in
   [RFC9909]: SHA-256 for the SHA2 128-bit parameter set, SHA-512 for
   the SHA2 192-bit and 256-bit parameter sets, SHAKE128 for the SHAKE
   128-bit parameter set, and SHAKE256 for the SHAKE 192-bit and 256-bit
   parameter sets.

   The contents of the parameters component for each algorithm MUST be
   absent.

4.  Use in X.509

   The following sections of [RFC9909] apply to the id-slh-dsa-_-24 and
   id-hash-slh-dsa-_-24-* object identifiers in the same way as to the
   id-slh-dsa-* and id-hash-slh-dsa-* object identifiers, respectively,
   with the sizes in Table 1:

   *  SLH-DSA Signatures (Section 4 of [RFC9909]).  Signatures are
      generated and verified with the algorithms of [FIPS205] named
      there, using the parameter set identified by the algorithm
      identifier and the empty context string, and are encoded as the
      raw octet string R || SIG_FORS || SIG_HT.

   *  Subject Public Key Fields (Section 5 of [RFC9909]).  The
      AlgorithmIdentifier for an SLH-DSA-FEW public key MUST use one of
      the id-slh-dsa-_-24 or id-hash-slh-dsa-_-24-* object identifiers
      from Section 3, and its parameters field MUST be absent.  The
      public key identifiers are defined in Appendix A.

   *  Key Usage Bits (Section 6 of [RFC9909]).  The requirements apply
      to certificates that indicate an id-slh-dsa-_-24 or id-hash-slh-
      dsa-_-24-* identifier in the SubjectPublicKeyInfo.

   *  Private Key Format (Section 7 of [RFC9909]).  The private key is
      the concatenation SK.seed || SK.prf || PK.seed || PK.root of
      length 4*n bytes, where n is 16, 24, or 32, depending on the
      security category.

   As in [RFC9909], a key identified by a Pure SLH-DSA-FEW OID is not
   permitted to be used with a HashSLH-DSA-FEW OID, and vice versa.  A
   key pair generated for an SLH-DSA-FEW parameter set MUST NOT be used
   with any other parameter set, including the [FIPS205] parameter set
   of the same security category and hash function.

5.  Operational Considerations

   This section is in addition to the Operational Considerations of
   [RFC9909], whose note on the very large (2^64) number of signatures
   does not apply to SLH-DSA-FEW.

   Unlike the parameter sets of [FIPS205], an SLH-DSA-FEW parameter set
   limits a single signing key to 2^24 signatures, a number that can be
   reached in practice (see Section 6).  Measures to stay within the
   limit include:

   *  tracking the number of signatures generated by each private key,
      including across all Hardware Security Modules (HSMs), backups,
      and replicas holding the same key, and refusing to sign or
      destroying the private key before the limit is reached;

   *  not sharing a private key between many signing devices;

   *  setting the certificate's "Not After" (expiration) date based on
      the remaining signature budget and the maximum aggregate signing
      rate across all copies of the key, and permanently disabling or
      destroying every private-key copy by that date; and

   *  using separate keys, such as a dedicated CRL signing key or a
      delegated OCSP responder key, for high-volume or automated signing
      operations.

   Although SLH-DSA is a stateless scheme, an operator using SLH-DSA-FEW
   needs a reliable signature count to stay within the limit.  A count
   that is lost, rolled back, or not shared between replicas can cause
   the limit to be exceeded unnoticed.

   SLH-DSA-FEW is not suited for keys that sign on demand in response to
   external requests, such as keys used for authentication in
   interactive protocols (for example, in TLS handshakes) or OCSP
   responder keys, unless the number of signatures can be bounded
   reliably.  Such keys SHOULD use the parameter sets of [FIPS205].

6.  Security Considerations

   The Security Considerations of [RFC9909] apply, except as changed
   below.

   [RFC9909] states that an SLH-DSA tree MUST NOT be used for more than
   2^64 signing operations.  This applies to the parameter sets of
   [FIPS205] only.  A key pair for an SLH-DSA-FEW parameter set MUST NOT
   be used for more than 2^24 signing operations.

   Beyond 2^24 signatures, the security of the key is no longer
   guaranteed to meet the security category listed in Table 1.  A
   relying party cannot detect that the limit has been exceeded: neither
   a certificate nor a signature reveals how many signatures have been
   generated with a key, and a forgery made possible by exceeding the
   limit is indistinguishable from a genuine signature.  Therefore,
   before using SLH-DSA-FEW, the operator MUST evaluate the operational
   environment of each signing key, taking into account at least:

   *  the number of physical or virtual devices that share the signing
      key,

   *  the maximum possible speed of each signing operation,

   *  the projected frequency of signature generation across all
      devices, and

   *  the intended operational lifetime of the key.

   If the evaluation and the operational controls cannot guarantee that
   no more than 2^24 signatures will be generated with a key, SLH-DSA-
   FEW MUST NOT be used for that key; the parameter sets of [FIPS205]
   can be used instead.

   All signing operations made with the key count against the limit,
   whether in Pure SLH-DSA or in HashSLH-DSA mode.  For a CA key, this
   includes signatures on certificates, CRLs, and, if the CA key is also
   used for this purpose, OCSP responses.  Because of this, SLH-DSA-FEW
   is best suited to keys that sign few objects, for example a code
   signing key or a CA key with a low issuance volume.

   According to [SP800-230], caching parts of or the whole SLH-DSA
   hypertree to speed up signing is permitted and does not affect the
   security properties of the algorithm.  Cached values are derived from
   the private key and need to be protected accordingly.

Appendix B.  Security Strengths

   The SLH-DSA-FEW parameter sets are defined for NIST security
   categories 1, 3, and 5; see Appendix B of [RFC9909] for the
   definition of the categories.  The resulting signature, public key,
   and private key sizes in bytes are listed in Table 1.  The HashSLH-
   DSA-FEW parameter sets have the same values as the Pure SLH-DSA-FEW
   equivalents.  These parameter sets are only secure for up to 2^24
   signatures per key; see Section 6.

   +================================+==========+=======+======+=======+
   | OID                            | NIST     | Sig.  | Pub. | Priv. |
   |                                | Category |       | Key  | Key   |
   +================================+==========+=======+======+=======+
   | id-(hash-)slh-dsa-sha2-128-24  | 1        | 3856  | 32   | 64    |
   +--------------------------------+----------+-------+------+-------+
   | id-(hash-)slh-dsa-shake-128-24 | 1        | 3856  | 32   | 64    |
   +--------------------------------+----------+-------+------+-------+
   | id-(hash-)slh-dsa-sha2-192-24  | 3        | 7752  | 48   | 96    |
   +--------------------------------+----------+-------+------+-------+
   | id-(hash-)slh-dsa-shake-192-24 | 3        | 7752  | 48   | 96    |
   +--------------------------------+----------+-------+------+-------+
   | id-(hash-)slh-dsa-sha2-256-24  | 5        | 14944 | 64   | 128   |
   +--------------------------------+----------+-------+------+-------+
   | id-(hash-)slh-dsa-shake-256-24 | 5        | 14944 | 64   | 128   |
   +--------------------------------+----------+-------+------+-------+

                 Table 1: SLH-DSA-FEW Security Strengths
